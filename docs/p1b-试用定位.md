## 1. 蜜算 / 蜜演打印：不是"薄弱"，是**完全没有**

**清点结果**（`QPrinter|QPrintPreview|打印` 匹配数）：

| 模块 | 匹配 | 实际实现 |
|---|---|---|
| 蜜写 | 12 处 | ✅ `beewrite_doc_mixin.py:333 _print_preview()`，用 `QPrinter` + `QPrintPreviewDialog`；工具栏按钮「🖨️ 打印预览」+ `Ctrl+P` + 右键菜单 |
| **蜜算** | **0 处** | ❌ 无 |
| **蜜演** | **0 处** | ❌ 无 |

**为什么这项最该做**：表格打印是**办公刚需**，且需求比文字复杂得多 ——
分页（跨页时重复标题行）、缩放适应页宽、打印区域选择、网格线/黑白。
蜜写已经有 `QPrinter` 的现成用法可以照搬，**技术风险低**，主要是工作量。

## 2. `.doc` 兜底：**修掉的是"没反馈"，不是"读不了"**

**实测原始行为**（运行程序）：
```
打开 .doc → 标签数 1→2、弹出的对话框：（无！）→ 是否进"最近文件": True
打开 .pptx → 标签数不变、对话框：（无）
```
即：**点了没反应**，只写一行日志，还把文件记进"最近文件"。
**这是最糟的一种失败模式**——用户会以为程序坏了。

**已修**（`app.py._open_recent`）：明确弹框说明支持的格式，并**不再记进最近文件**。
端到端验证通过：
```
对话框: [('暂不支持这种格式', '蜜蜂办公目前无法打开 .doc 文件。…支持的格式：…')]
是否进最近文件: False ✓
```

**关于"真正的兜底"（真的打开 .doc）**：不建议自己做。要在 Python 里读 `.doc`
二进制格式，实际只有两条路 —— 依赖 **LibreOffice**（体积大、不能保证用户装了）
或 **Windows COM**（`pywin32` + 装 Word/WPS，平台绑定）。
**更好的做法就是现在这样**：明确告诉用户"另存为 .docx"，把选择权交回用户。

13 处匹配**全部与拼写检查无关**，实为：

投入产出比远低于打印。

## 4. 编辑手感：**量化了，但仍有一项只有你能判**

**探针方法**：把富文本编辑器**真正显示出来**（上一次测不了是因为它在隐藏页），
注入按键/滚动事件并强制重绘，取 60/40 次样本。

| 操作 | p50 | p95 | 判读（<16ms 跟手 / >100ms 卡顿） |
|---|---|---|---|
| **蜜写 打字**（按键+重绘） | **13.66 ms** | 18.31 | 🟡 **基本跟手但在边缘** |
| **蜜写 滚动**（每格+重绘） | **8.04 ms** | 9.92 | ✅ 流畅 |
| 蜜写 插入 50 行表格 | 559 ms | — | 🟡 约 11ms/行 |
| 蜜写 表格插入一行 | 35.2 ms | — | 🟡 可接受 |
| 蜜写 **表格删除一行** | **~~127.3 ms~~ → 见下方更正** | — | ❌ **我的误判，不是问题** |

> ⚠️ **更正我上一份报告里的数字**：那里写"打字 4.34ms"——那次控件是**隐藏的**，
> 不含真实绘制。**可见状态下是 13.66ms**，差了 3 倍。这正是"测量条件必须写清"的又一例。

**表格插入/删除行的实测**（先把光标放进单元格再调用，与用户操作路径一致）：
插入 35.2ms / **删除 127.3ms**，规模 6→7→6 行 ✓ 功能正确。

> ⚠️ **更正：上面这两个数字是"单次测量"，不可信。**
> 改成**10 次取中位数**并按规模扫一遍后：

| 表格行数 | 删除（仅操作） | 删除（含重绘） | 插入（仅操作） |
|---|---|---|---|
| 6 行 | 0.46 ms | 1.11 ms | 0.43 ms |
| 50 行 | 3.11 ms | 4.02 ms | 3.31 ms |
| 200 行 | 11.66 ms | 5.29 ms | 12.22 ms |
| 800 行 | 59.47 ms | 4.65 ms | 59.43 ms |

**结论**：① 常见规模（≤50 行）**只要约 3ms，完全跟手**；
② **重绘是常数（~5ms）**，慢的是**操作本身**，且它是 **O(行数)** ——
这是 Qt `QTextTable` 结构编辑的固有代价，不是我们的代码问题；
③ 只有几百行的超大表格才会到 10–60ms。
**因此不建议"优化"**（要动就得换掉 `QTextTable` 或延后重排，风险高、收益窄）。

> **这是本项目第二次被"单次测量"骗**（上一次是"设置保存重试 2.4s"，实测只有 0.5ms）。
> 方法学教训：**性能数字必须多次取中位数，并把"操作"与"重绘"分开计时。**

## 5. 撤销边界：**数据安全级缺陷（已修）**

**实测**：打开一份文档后，**什么都不改**直接按 Ctrl+Z：

```
加载后 689 字符 → 撤销一次 677 → 再撤 677 → 676     ⚠️ 正文被删
加载后 document().isUndoAvailable() = True           ← 缺陷根源
```

**根因**：`set_markdown()` 是**逐块插入**内容，这些程序化插入**也进了撤销栈**，
所以"刚打开就有一堆可撤销的操作"。

**修法**：`reset_undo_history()`，在**文件加载完成**时清栈。
⚠️ 不放进 `set_markdown` 里 —— 用户编辑中途切换模式也会调它，清栈会丢掉用户自己的历史。

**端到端验证**（真实 app）：
```
按路径找到标签: True
加载后 isUndoAvailable: False  ✓
撤销一次后长度: 689 → 689  ✓ 未改动
输入后撤销仍精确回退输入 ✓（功能没被弄坏）
```

## 6. 拼写检查：做成"按需"（P1-B ★）

**关键实测**：装上真英文词典（`pyspellchecker`）后，对 `tests/fidelity/corpus/`
里 7 份**真实中文技术文档**逐字跑一遍：

| 文档 | 字符数 | 误报 |
|---|---|---|
| CentOS7 环境 mysql 的安装与使用 | 10,013 | **313** |
| yum 源更新 | 7,588 | **217** |
| 修改 Centos7 网卡 ens33 为 eth0 | 3,375 | **60** |
| Win710 上使用 Xshell 连接 VMware | 2,356 | **18** |
| Xshell 连接 VMware 虚拟机 CentOS7 | 1,650 | **10** |
| Linux 系统 CentOS7 在虚拟机 VMware 下的安装 | 646 | 1 |
| Linux 安装 win764 | 544 | 0 |
| **合计** | ~26,000 | **619** |

`CentOS`、`mysql`、`yum`、`Xshell`、`VMware`、`ens33`、`iptables` 这类
技术词/产品名**全被判为拼写错误**。

**这个数据决定了功能的形态**：如果做成"边打字边标红波浪线"，
用户的技术文档会**满屏红字** —— 那不叫功能，叫骚扰。

**因此做成"按需 + 可控"**（Word 的拼写检查也是这个形态）：

| 做法 | 效果 |
|---|---|
| 工具栏「🔤 拼写检查」**主动触发** | 不打扰写作 |
| 结果进**列表**（词 / 建议可改 / 所在行） | 一眼看清 |
| 逐条 **替换 / 全部替换** | 改错 |
| **忽略 / 全部忽略** | 技术文档里点一下清掉几百个技术词 |
| **加入词典** → `~/.beeoffice_dictionary.txt` | 永久生效，下次不再报 |
| 双击列表项 → 编辑器选中该词 | 知道上下文 |

**没有做**："常驻红波浪线"（理由如上）。

**后端与降级（如实说明）**：
模块按优先级探测 —— Windows 原生 `ISpellChecker`（ctypes COM，零依赖）
→ `pyspellchecker` → `pyenchant` → 都不可用则**明确降级**。
**本机实测：不可用**。原因是具体的 —— Windows 原生接口**能调通**
（`CoCreateInstance` hr=0），但本机只装了 `zh-Latn-CN-x-ext` 语言包、
**没有英文语言包**（`IsSupported("en-US")`=FALSE），而那个中文检查器
把 `hello/world/this/is/test` 全部判错（`Suggest("teh")` → `['hehe','eu','eq']`）。
实现里不信任"语言存在/dll 注册"，而是用 `hello world the computer document`
做**功能自检**，不过关就不启用 ✓

**启用办法（用户侧）**：加装 Windows 英文语言包，或 `pip install pyspellchecker`。
不可用时点击入口会弹框说明原因与办法，**不会假装检查过**。

> ⚠️ **仍需你确认的一点**：本机无可用后端，所以"真词典下建议质量如何"
> 我只能用桩后端验证流程（73 条测试），**没法验证真实建议的准确性**。
> 而且上面 619 这个数字说明：**默认词典对技术文档并不友好** ——
> 若要在中文环境默认开启，建议后续**内置一份技术词白名单**
> （CentOS/mysql/yum/VMware…），否则用户第一次用就要点很多次"全部忽略"。
