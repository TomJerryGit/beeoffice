# 首次打开 DOCX 剩余优化（v5.0.17，2026-10-21）

> 前置：v5.0.13 已把 5 万字文档首次打开从 **5.85 s** 降到 **~0.83 s**
> （样式查找 O(N²) 修复 + 后台导入）。本轮针对"剩余约 0.8 s"做分段剖析，
> 继续把**主线程阻塞**降下来。所有数字都标注了测量方式与环境限制。

---

## 0. 一页结论

| 指标（5 万字 DOCX） | 优化前（8829451） | 优化后 | 变化 |
|---|---:|---:|---|
| 主线程 `read_docx_extras` | **122–164 ms** | **0 ms**（挪到后台） | −100% |
| 主线程 `analyze_file`（保真提示） | 5–6 ms | **0 ms**（挪到后台） | −100% |
| 主线程渲染 `set_content` | 383–604 ms | **179–207 ms** | −50% 左右 |
| 装载期光标通知（主线程） | ~250 ms + 10,860 次 hasattr | 跳过 | 消除 |
| `_new_word_doc`（首次，含懒加载） | **1,179–1,542 ms** | **102–325 ms** | −75% 左右 |
| 端到端首次打开（wall-clock，3 次取中位/范围） | **5.67–8.38 s** | **2.07–2.37 s** | 约 −60% |
| 2.54 MB 带图文档端到端 | 0.78–1.26 s | 0.73–0.78 s | 略降/持平（图像解码占主导） |
| `import beeoffice.plugins.beewrite` | 1,390 ms | **840 ms** | −40% |
| 首开时是否加载 pandas/matplotlib | 是 | **否**（延迟到使用点） | 消除 |

**注意**：这是离屏（offscreen）、本机虚拟化环境、冷/热混合的测量；绝对值有波动，
**相对改善**才是结论。2.54 MB 带图文档仍主要耗在图片解码（24 张图 ~160 ms），本轮未动。

## 2. 改了什么（四处，均可单独回滚）

### 2.1 后台线程一次性准备全部数据（`beeoffice/app.py`）

新增模块级 `_import_docx_for_open(path)`：在后台线程里依次完成
`import_from_docx` → `read_docx_extras` → `analyze_file`，返回三元组；
`_open_docx_file` 的 on_result 只做 Qt 控件操作与 `apply_docx_extras`。
`_attach_fidelity_report(widget, path, report=None)` 支持传入后台预算的报告，
不再在主线程重复 XML 分析（兼容旧调用）。

### 2.2 装载期间跳过"光标通知/格式状态"（3 个文件）

`set_markdown` 是逐块插入，每块触发 `cursorPositionChanged`：

- `_notify_cursor_position`：装载时直接 return（原先每段沿父链 `hasattr` 探测，
  5 万字实测 1,810 次通知、10,860 次 hasattr，约 250 ms）；
- `_update_cursor_position` / `_update_format_state`：装载期间跳过（约 50 ms）。

### 2.3 `data_binding.py`：pandas 延迟导入

`data_binding` 被 `beewrite.py` 顶层导入，原先顶层 `import pandas`（~0.6 s）。
现在只做 `_pandas()` 懒加载：`register_file` / `_format_value` 才导入。
没有数据绑定的文档首开不再为 pandas 买单；绑定功能行为不变。

### 2.4 `beewrite_formula.py`：matplotlib 延迟导入

公式对话框模块被 `beewrite` 顶层导入，原先顶层 `matplotlib.use("Agg")` +
`import matplotlib.pyplot`（~0.45 s）。现在 `HAS_MPL` 用
`importlib.util.find_spec` 探测，真正渲染公式时 `_load_pyplot()` 才导入。
插入公式功能行为不变。

## 4. 剩余（如实）

- `_new_word_doc` 首次调用仍含 `import beeoffice.plugins.beewrite`（~0.84 s，一次性）。
  进一步做法是把插件模块**在启动空闲期预热**（后台线程）——收益是首开更快，
  代价是启动期多占 CPU，本轮未做；
- 带大图文档的剩余耗时主要是**图片解码/插入**（~160 ms/24 张），属必要工作；
- 纯文字 5 万字文档主线程渲染仍 ~180–200 ms（1093 个 block 的 QTextCursor 插入），
  若继续压需要改 `set_markdown` 的分块策略（合并空块/批量插入），会影响空行语义，
  本轮**不做**（避免为性能改坏保真）。
