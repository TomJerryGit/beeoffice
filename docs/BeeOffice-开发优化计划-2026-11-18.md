# BeeOffice 开发优化计划（2026-11-18 起）

## 1. 目标与边界

**目标**：未来 12 周完成 Phase 0 + Phase 1 主体，使项目进入“可签名、可干净机验收、真实文档往返 ≥85%”的 v6.0 候选轨道。

**边界**：

- 冻结新功能，只做保真、架构、信任、稳定性；
- 不新增 P2 功能；
- 不再发功能型 Beta；
- 每周有可验证产出，禁止长期大分支。

**团队假设**：核心开发 1 人 + 兼职 QA/发布 0.5 人。

---

## 2. 开发节奏

| 周期 | 活动 |
|---|---|
| 每日 | 构建 + 目标测试 + 记录阻塞 |
| 每周五 | 周验收：测试、语料回归、风险复盘 |
| 每两周 | 阶段门禁评审 |
| 每月 | 发布一次内部 RC/快照 |

分支策略：

```text
main          受保护，始终可构建
feat/*        单任务分支，≤3 天
fix/*         缺陷修复
release/x.y   发布冻结
```

Definition of Done：

```text
代码 + 测试 + 文档 + CI 通过 + 真实回归（如适用）
```

---

## 5. 工程规范

- 每个任务必须有：issue、验收标准、测试、回归样本；
- 禁止跨模块直接访问私有属性；
- 新增文件遵循 LF/CRLF 约定，提交前检查 diff；
- 适配器层必须有契约测试；
- 真实 Office 验收脚本不通过，不得标记完成；
- 发布前必须跑 `release_check` + 全量测试 + 语料回归。

## 6. 容量与排期

| 角色 | 每周投入 | 主要工作 |
|---|---|---|
| 核心开发 | 5 天 | 保真/架构/对象 |
| 兼职 QA | 2.5 天 | 语料、干净机、验收 |
| 预留缓冲 | 20% | 缺陷/外部依赖 |

排期原则：

- 每周至少 1 个可交付结果；
- 高风险任务（签名、干净机）提前 2 周启动；
- 架构任务不超过总容量 30%；
- 保真任务优先于体验优化。

## 8. 风险与应对

| 风险 | 应对 |
|---|---|
| 证书采购慢 | 第 1 周启动，准备 OV 备用 |
| 干净机不可用 | Hyper-V 模板 + 云 VM 备选 |
| 保真修复反复 | 先建语料与差异报告，再改代码 |
| 架构改造拖慢交付 | 绞杀者模式，禁止大重写 |
| 单人精力不足 | 砍 P2，优先 Word/Excel |
| 网络/推送不稳定 | 本地 tag/产物 + 重试脚本 |
