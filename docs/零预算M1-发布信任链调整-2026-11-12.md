# 零预算 M1 调整：发布信任链

日期：2026-11-12  
约束：**不采购代码签名证书；不购买云 VM/新机器。**

## 1. 结论

原 M1 的“可信发布门禁”在当前预算下**无法完整达成**：

```text
签名证书：需要费用或 OSS 免费签名资格
干净 Win10 VM：需要云 VM、新机器或本地 ISO + 虚拟化
```

因此 M1 拆成两条线：

| 线 | 目标 | 预算 | 状态 |
|---|---|---|---|
| **M1A 零成本门禁** | CI 硬门禁 + 哈希 + 安装冒烟 + 发布清单 + Beta 标识 | 0 元 | 可立即做 |
| **M1B 外部资源** | 代码签名 + 干净 Win10 验收 | 需证书/VM | 暂缓、登记为 Stable 阻塞项 |

> 在 M1B 完成前，后续版本只能标 **Beta / Unsigned**，不得称“稳定版/可信签名版”。

## 2. M1A：现在就能做的零成本部分

### 2.1 CI 硬门禁

- 全量测试任务改为阻塞（先跑基线，确认稳定后移除 `continue-on-error`）；
- 新增 `tools/security_scan.py`，高危 >0 阻止合并；
- 新增 `tools/coverage_gate.py`，核心模块 <100% 阻止合并；
- main 分支保护，要求以上检查通过；
- 保留安装/卸载冒烟 workflow（已通过）。

### 2.2 发布清单自动化

新增 `tools/release_check.py` 或 PowerShell 脚本，发版前检查：

```text
[ ] 版本号与 CHANGELOG 一致
[ ] 全量测试通过
[ ] 核心覆盖率 100%
[ ] 安全扫描高危 0
[ ] ZIP/安装包存在
[ ] SHA-256 文件与资产一致
[ ] ZIP testzip 通过
[ ] 安装/卸载冒烟通过
[ ] Release 说明包含未签名/未干净机验收/Win11 未验证
```

### 2.3 免费的可追溯性（替代“签名”的一部分）

- GitHub Artifact Attestations / Sigstore keyless：
  - 免费；
  - 能证明产物由指定 workflow/commit 构建；
  - **不能**替代 Windows Authenticode，**不能**消除 SmartScreen。
- 继续提供 SHA-256 校验文件；
- Release 说明明确“无 Authenticode 签名”。

### 2.4 零成本干净环境预检

以下只能作为**预检**，不能写成“干净机验收”：

| 方式 | 成本 | 局限 |
|---|---|---|
| GitHub Windows Server runner | 0 | 不是 Win10/11 客户端 |
| Windows Sandbox | 0 | 需启用 Hyper-V/重启；与 VMware 14 可能冲突 |
| VirtualBox + 官方 Win10 ISO | 0 | 需手动下载 ISO；8 GB 宿主需低配 |
| 免费云试用额度 | 0（有限期） | 需账号/信用卡；可能受限 |

## 3. M1B：需要外部资源，暂缓

### 3.1 代码签名（零预算候选，不保证）

- **SignPath Foundation**：面向开源项目的免费签名计划，需要申请/审核；
- Azure Trusted Signing / 云厂商免费额度：有期限和资格限制；
- 自签名证书：免费，但**不会获得 SmartScreen 信任**，只适合内部完整性验证，不建议对外宣传“已签名可信”。

### 3.2 干净机验收

- 免费云试用额度 + Win10 22H2 镜像；
- 本地 VirtualBox + 官方 ISO（需要手动下载）；
- 新机器/借用机器。

**M1B 完成前，Stable 发布门禁保持未通过。**

## 4. 修订后的发版门禁

### Beta / Unsigned 可发布条件

```text
[ ] 全量测试通过
[ ] 核心覆盖率 100%
[ ] 安全扫描高危 0
[ ] 构建 + SHA-256
[ ] ZIP testzip OK
[ ] 安装/卸载 Server 冒烟通过
[ ] GitHub artifact attestation（启用后）
[ ] Release 明确写“未签名、无干净机验收、Win11 未验证”
```

### Stable 发布条件（当前不满足）

```text
[ ] 有效 Authenticode 签名
[ ] 干净 Win10 22H2 验收记录
[ ] 上述 Beta 条件全部满足
```

## 5. 建议执行顺序

1. **本周**：M1A CI 门禁 + 发布清单 + attestation；
2. **本周**：把 v5.4.5/v5.4.6 标为 Beta/Unsigned，不称稳定；
3. **持续**：申请 SignPath Foundation / 观察免费签名资格；
4. **有环境时**：Windows Sandbox 预检 → 免费云 VM 或 VirtualBox 正式验收；
5. **M1B 完成后**：再开放 Stable 渠道。

## 6. 结论

零预算下仍然可以把**工程质量门禁**做得很好，但**无法获得 Windows 代码签名信任和真实干净机结论**。  
因此路线图改为：

```text
M1A：零成本工程门禁（现在做）
M1B：签名 + 干净机（资源允许再做）
Stable：M1B 完成前不发布
```

这不是降低标准，而是把“能做的”和“需要资源的”分开，避免用未签名/未验收产物冒充稳定版。
